# Техническая архитектура

Документ описывает, как Slice устроен на уровне блокчейна и вне его: технический
стек, 11 Anchor-программ, модель данных, жизненный цикл актива, механики
голосований и слой вне блокчейна. Бизнес-смысл ролей и процесса — в
[solution.md](solution.md).

## Три слоя

```
Клиент (браузер)  →  Бэкенд (координатор)  →  Solana (источник истины)
   Next.js 16          Elysia · Bun · Postgres        Маршрутизатор + 11 программ
```

- **Клиент** — Next.js 16 (App Router), пользователь сам подписывает транзакции,
  касающиеся его кошелька. Фронтенд не хранит приватных ключей.
- **Бэкенд** — координатор, а не источник истины. Агрегирует данные, кеширует
  состояние блокчейна в Postgres, держит стакан ордеров вторичного рынка вне
  блокчейна. Не может инициировать транзакцию от имени пользователя; если бэкенд
  откажет, пользователь отправляет транзакцию напрямую с кошелька.
- **Solana** — источник истины. Всё значимое состояние живёт в смарт-контрактах.

### Технический стек

| Слой | Технологии |
|------|-----------|
| В блокчейне | Rust, фреймворк Anchor, 11 программ, Token-2022, подписи Ed25519 |
| Бэкенд | Bun, веб-фреймворк Elysia, TypeScript, Drizzle ORM, PostgreSQL 16 |
| Фронтенд | Next.js 16 (App Router), React 19, Tailwind CSS v4, shadcn/ui, @solana/wallet-adapter |
| Идентичность | Ory Kratos (email + TOTP, OAuth, привязка кошелька) |
| Хранилище документов | Irys поверх Arweave |

### Почему Solana

| Критерий | Ethereum | Polygon | Solana |
|---|---|---|---|
| Финальность | 12–60 сек | 2–3 сек | **400 мс** |
| Комиссия | $0.50–20 | $0.01–0.10 | **$0.00025** |
| TPS | 15–30 | 65 | **65 000** |
| Встроенные фракции | — | — | **Token-2022** |
| Инструменты разработчика | Hardhat | Hardhat | **Anchor** |

Сделки с активами частые и мелкие: $0.50 комиссии × 100 инвесторов = $50 только
на блокчейне. На Solana то же самое стоит ~$0.025. Финальность 400 мс не оставляет
инвестора в подвешенном состоянии, а расширения Token-2022 дают встроенные
перехватчики при передаче — это нужно для проверок соблюдения требований.

## Архитектура в блокчейне

### Паттерн «маршрутизатор + модули»

Единая точка входа — **маршрутизатор**. Программы-модули регистрируются в нём;
все межпрограммные вызовы (CPI) идут через маршрутизатор. На каждый вызов
маршрутизатор проверяет KYC, наличие зарегистрированного модуля и инструкцию в
белом списке. Обновление любой программы — это замена адреса в маршрутизаторе без
миграции данных. Подход — аналог EIP-2535 (Diamond) из Ethereum, адаптированный
под Solana.

### Модель PDA

Каждое состояние хранится по **программно-производному адресу (PDA)** —
детерминированному адресу, вычисляемому из набора ключей (seeds), например
`[program, entity, id]`. Клиент сам вычисляет адрес и не зависит от глобальных
индексов или списков в блокчейне.

### 11 Anchor-программ

11 программ + маршрутизатор = 12 развёртываний на Solana. Каждая программа
отвечает за одну задачу.

| Группа | Программы | Назначение |
|--------|-----------|-----------|
| Identity & Assets | `identity`, `asset_registry`, `validation` | Кто ты, чем владеешь, кто проверил |
| Deals | `agreement`, `execution` | Прямые P2P-сделки между кошельками |
| Tokens | `appraisal`, `vault`, `auction` | Оценка, фракции, сбор средств, выкуп |
| Governance | `compliance`, `market` | Нотариусы, юристы, комиссии, вторичный рынок |

Отдельная программа управления отвечает за **децентрализованное назначение
нотариусов** (см. ниже) — её методы `propose_notary` / `confirm_notary` /
`ping_heartbeat`.

**Что делает каждая программа:**

- **`identity`** — корень системы. PDA: `User[wallet]` (профиль),
  `UserReputation[wallet, role]` (репутация отдельно по каждой роли),
  `KycAttestation[wallet, provider]` (KYC, с проверкой срока действия),
  `PublicKeyRecord[owner, key]` (ключи для подписей вне блокчейна). Роли заданы
  enum `UserRole`: `Regular`, `Verifier`, `Appraiser`, `Lawyer`, `Notary`,
  `Admin`. Один кошелёк может иметь любое их подмножество.
- **`asset_registry`** — жизненный цикл актива. `Asset` PDA хранит `asset_id`,
  владельцев, `status` (enum из 12 состояний), счётчик и порог верификаций,
  `minimum_price`, ссылки на хранилище и эмитент фракций, данные юриста и
  `spv_document_hash`. `set_asset_status` может вызвать только уполномоченная
  программа. `AssetAttribute[asset_id, key_hash]` — произвольные пары
  ключ/значение (город, площадь, год).
- **`validation`** — верификаторы подписывают факты об активе вне блокчейна
  ключами Ed25519; программа проверяет подпись через Instructions sysvar. По
  достижении порога верификаций актив переходит в статус NotaryPreCheck.
- **`agreement` / `execution`** — структура прямой сделки (стороны, цена,
  условия) и атомарный расчёт с условным депонированием. Запасной путь для
  нефракционной торговли.
- **`appraisal`** — слепое двухфазное голосование «конверт и вскрытие» (до 11
  оценщиков на раунд).
- **`vault`** — создаёт эмитент Token-2022, держит запас фракций и распределяет
  их инвесторам после сбора средств.
- **`auction`** — кампании сбора средств (вход) и аукционы выкупа (выход с
  голосованием держателей).
- **`compliance`** — раунды нотариусов (PreCheck/PostCheck), очередь юридических
  задач, конфигурация комиссий `FeeConfig`.
- **`market`** — вторичный рынок: сведение ордеров и расчёт.

### Модель данных (основные PDA)

```
User[wallet]                  → KycAttestation, UserReputation, PublicKeyRecord
Asset[asset_id]               → AssetVerification, AppraisalRound, NotaryRound,
                                Vault, BuyoutAuction
AppraisalRound[asset_id]      → AppraisalCommit (хеши и раскрытия оценщиков)
NotaryRound[asset_id, type]   → NotaryVote (взвешенные голоса нотариусов)
Vault[asset_id]               → FractionMint (Token-2022), Deposit[asset_id, investor]
BuyoutAuction[asset_id]       → BuyoutVote (голоса держателей по балансу)
```

Все PDA выводятся из seeds детерминированно — глобальных реестров в блокчейне нет,
клиент всегда знает, где искать конкретную запись.

### NFT против фракционных токенов

Slice использует оба типа токенов: уникальный NFT — чтобы зафиксировать «эта
конкретная квартира» (регистрация через `asset_registry`), и взаимозаменяемые
фракции Token-2022 — чтобы разделить актив на доли. У фракций `supply = N`
(параметр), `decimals = 0`, метаданные в блокчейне; одна фракция = `1/N` доли
актива.

### Связь блокчейна с реальным миром

`Asset` PDA в блокчейне хранит хеш документов SPV. SPV (в Казахстане — SPC)
юридически владеет реальным активом. Если документы подменят — хеш не совпадёт, и
это будет видно всем. Владение фракциями → доля в SPV → право на долю реального
актива.

### Перехватчики при передаче (Token-2022)

Каждый перевод фракций проходит через transfer hook, который проверяет:

1. **KYC обеих сторон** — у отправителя и получателя действующее подтверждение;
2. **Актив не заморожен** — нет ареста или спора;
3. **Лимит на держателя** — новый баланс не превышает `max_per_holder` от запаса
   (защита от «китов», anti-whale).

Если хоть одна проверка не прошла — транзакция отклоняется. Охранник встроен в сам
токен, его нельзя обойти никаким кошельком.

## Жизненный цикл актива

`Asset.status` — это автомат из **12 состояний**. Каждый переход авторизуется
ровно одной уполномоченной программой. Полная схема:

```
PendingVerification → NotaryPreCheck → Verified → PendingEvaluation → Evaluated
  → Funding → InLegalPool → LegalProcessing → LegallyBound → NotaryPostCheck
  → Fractionalized → Dissolved
```

- **Верификация** (~3–5 дней): актив зарегистрирован → набран порог верификаций →
  взвешенный кворум нотариусов одобрил → `Verified`. Провал → `Rejected`.
- **Оценка** (~14 дней): 7 дней запечатывания + 7 дней вскрытия → медиана
  записывается как `minimum_price` → `Evaluated`.
- **Сбор средств** (~30 дней): создано хранилище → инвесторы вносят средства. При
  достижении цели → `InLegalPool`; при провале — возврат всем, актив снова
  `Evaluated`.
- **Юридическое оформление** (~30 дней): юрист берёт задачу → `LegalProcessing` →
  загрузил хеш SPV → `LegallyBound` → `NotaryPostCheck`. Кворум нотариусов одобрил
  SPV → `Fractionalized`. Юрист пропустил 30-дневный дедлайн → штраф, задача
  возвращается в общий пул.
- **Рынок и выход**: `Fractionalized` — активная торговля, может длиться годами.
  Принятый выкуп → `Dissolved` (хранилище закрыто, фракции сожжены, SPV
  перерегистрирован на покупателя).

Любой статус до сбора средств может перейти в `Cancelled`. Типичная шкала от
регистрации до первой торговли — **180 дней**; узкие места — оценка (в темпе
человека) и юридическое оформление.

## Механики голосований

В Slice семь точек голосования с четырьмя разными механиками:

| # | Момент | Участники | Вес голоса | Результат |
|---|--------|-----------|-----------|-----------|
| 1 | Notary PreCheck | общий пул нотариусов | по репутации | verify / reject |
| 2 | Notary PostCheck | общий пул нотариусов | по репутации | fractionalize / requeue |
| 3 | Оценка | до 11 оценщиков | равный (штраф за крайнее) | медианная цена |
| 4 | Юридическая задача | общий пул юристов | кто первый, тот и забрал | задача назначена |
| 5 | Сбор средств | все KYC-инвесторы | по сумме депозита | funded / refund |
| 6 | Вторичная сделка | покупатель + продавец | двусторонний матч | атомарный обмен |
| 7 | Выкуп | держатели фракций | по балансу фракций | dissolve / refund |

- **Взвешенное пороговое голосование (нотариусы).** Вес голоса:
  `vote_weight = max(1000, 10000 + rating_score × 10)`. Хороший нотариус
  (rating = +500) весит 15 000, плохой — минимум 1000. Кворум считается по сумме
  весов, обычно `quorum_bps = 6666` (66.66%). Взвешивание защищает от атак Сивиллы.
- **Медиана через «конверт и вскрытие» (оценка).** Оценщики равны по весу,
  честность обеспечивается залогом и штрафом за отклонение от медианы.
- **Гонка за задачей (юристы).** Не голосование: первый юрист, атомарно
  захвативший задачу из очереди, получает 30 дней на работу.
- **Голосование держателей по балансу (выкуп).** Вес = баланс фракций (1 фракция
  = 1 голос). Покупатель блокирует `offer_per_token × total_supply` до завершения.

## Слой вне блокчейна

- **Координатор на бэкенде.** Пользователь подписывает транзакцию → бэкенд
  добавляет метаданные и отправляет её → обновляет кеш. Бэкенд не имеет монополии:
  при отказе пользователь шлёт транзакцию напрямую с кошелька.
- **Кеширование.** Индексатор подписывается на логи программ Solana, парсит
  события Anchor и пишет их в Postgres. API читает из кеша, при промахе — напрямую
  из блокчейна. Источник истины всегда блокчейн; Postgres можно перестроить.
- **Интеграции.** *Ory Kratos* — управление идентичностью (email + TOTP, OAuth,
  привязка кошелька через подпись). *Irys / Arweave* — неизменяемое хранилище
  документов: файл в Irys, хеш — в блокчейне. *KYC-провайдеры* (Sumsub, Binance,
  Civic) — пока mock-реализация; подтверждения приходят webhook'ом и пишутся в PDA
  `KycAttestation`. *PostgreSQL* — кеш данных блокчейна, стакан ордеров, сессии.

### Децентрализованные нотариусы

Отдельная программа управления назначением нотариусов в блокчейне:

- **GlobalState** — 10 стартовых нотариусов при запуске системы;
- **добавление нового** — 3 голоса активных нотариусов создают нового;
- **контроль активности** — 90 дней без сигнала активности → статус `inactive`,
  180 дней → возможно восстановление;
- **аварийный режим** — если активных нотариусов меньше 3, система замораживается.

Нотариусы не назначаются платформой — только кворумом действующих нотариусов. Это
защита от централизации.

### Два маршрута пользователя

Бэкенд прячет блокчейн, поэтому платформа поддерживает две модели работы (см.
также [roadmap-and-risks.md](roadmap-and-risks.md)):

- **«Как обычный сайт»** — регистрация по email + TOTP, бэкенд выдаёт
  кастодиальный кошелёк (ключи зашифрованы на бэкенде), пользователь может вообще
  не знать, что это блокчейн. Аналог Binance, Coinbase, Revolut Crypto.
- **«Самостоятельное хранение ключей»** — подключение Phantom / Solflare, подписи
  в клиентском кошельке, полный контроль и прямое взаимодействие с контрактами.

Между маршрутами можно переходить в обе стороны: экспортировать ключ из веб2-режима
или привязать email для восстановления доступа в веб3-режиме.
